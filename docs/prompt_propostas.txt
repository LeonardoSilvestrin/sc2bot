```text
Attention
    ↓
Awareness
    ↓
Ego
    ↓
Body
```

Antes de alterar qualquer código, leia integralmente:

```text
docs/propostas.md
```

Esse documento contém uma análise do estado atual do bot, comparações com bots/frameworks open source de StarCraft II, problemas concretos observados, recomendações arquiteturais e um roadmap priorizado.

Use `docs/propostas.md` como fonte principal para decidir **o que melhorar**, mas não interprete o documento como autorização para criar novas camadas arquiteturais.

# Princípio arquitetural não negociável

A arquitetura principal deve continuar sendo:

```text
Attention
→ Awareness
→ Ego
→ Body
```

Novos conceitos devem morar dentro dessas quatro responsabilidades.

Não crie novas camadas intermediárias como:

```text
ThreatSystem
RegionalIntelligence
CombatAssessment
DecisionEngine
MissionManager
TacticalLayer
PlanningLayer
WorldModelLayer
```

se elas apenas reorganizarem conceitos que já pertencem a Attention, Awareness, Ego ou Body.

Submódulos internos são permitidos e desejáveis quando um arquivo crescer demais, mas eles não devem introduzir novas autoridades decisórias.

Exemplo aceitável:

```text
awareness/
    memory/
    spatial/
    regions/
    threats/
```

Isso continua sendo Awareness.

Exemplo indesejado:

```text
attention/
awareness/
threat_system/
regional_intelligence/
decision_layer/
ego/
body/
```

A meta é especialização interna sem recriar a burocracia da antiga branch `matematização`.

---

# Responsabilidades das quatro camadas

## 1. Attention

Attention representa:

> O que o bot consegue observar diretamente agora?

Ela pode conter:

* unidades visíveis;
* estruturas visíveis;
* recursos e estado do frame;
* posições;
* eventos observáveis;
* geometria estática do mapa;
* expansões;
* regiões, passagens e chokes derivados da geometria física;
* fatos diretamente extraíveis do jogo.

Attention não deve decidir:

* se uma região é segura;
* se devemos atacar;
* qual ameaça merece resposta;
* quanto exército deve ser enviado;
* qual missão tem prioridade.

Attention produz fatos.

---

## 2. Awareness

Awareness representa:

> O que o bot acredita sobre o mundo a partir dos fatos, memória e inferência?

Ela deve ser a casa natural de conceitos como:

* enemy memory;
* last seen;
* confidence;
* uncertainty;
* known enemy power;
* estimated enemy power;
* possible threat;
* threat/influence fields;
* control;
* information age;
* enemy force estimation;
* ThreatIncident;
* RegionState;
* base threat state;
* estimativas espaciais.

Importante:

Awareness descreve o mundo.

Ela não escolhe política.

Por exemplo:

```text
incident_power = 12.4
confidence = 0.71
affected_bases = [natural]
```

é Awareness.

Mas:

```text
required_power = 18.6
```

não deve ser automaticamente Awareness, porque contém uma decisão de política sobre margem defensiva.

Da mesma forma:

```text
region.control = -0.4
region.enemy_power = 20
region.information_age = 35 s
```

é Awareness.

Enquanto:

```text
"não atacar essa região"
```

é Ego.

### ThreatIncident

Se `docs/propostas.md` recomendar `ThreatIncident`, implemente-o como uma representação de Awareness.

Um incidente pode agregar:

* contatos relacionados;
* poder inimigo estimado;
* tipo/capacidades da ameaça;
* confiança;
* posição/região;
* bases ou ativos afetados;
* direção provável;
* tempo desde observação;
* ground/air compatibility.

Um mesmo incidente não deve virar automaticamente uma missão por base.

O objetivo é corrigir situações como um único inimigo gerando múltiplas respostas defensivas independentes.

---

## 3. Ego

Ego representa:

> Dado o que acreditamos sobre o mundo, o que queremos fazer?

Aqui permanecem:

* Strategy;
* planners;
* escolha de objetivos;
* avaliação de oportunidade;
* avaliação de risco estratégico;
* required power;
* target selection;
* mission/proposal creation;
* utility entre opções comparáveis;
* attack / defense / intel / economy intent.

Os planners decidem **o quê** deve acontecer.

Exemplo para Defense:

```text
Awareness:
incident_power = 10
current_suitable_cover = 4

Ego / Defense Planner:
required_power = defensive_margin × incident_power
reinforcement_deficit = max(
    0,
    required_power - current_suitable_cover,
)
```

Essa separação é importante:

```text
incident_power
```

é uma estimativa sobre o mundo.

```text
required_power
```

é política.

O planner pode então produzir algo como:

```text
DefenseProposal
    minimum_power
    desired_power
    required_capabilities
    preferred_capabilities
    target
    urgency
    lifecycle
```

Não transforme isso prematuramente em um sistema genérico universal de missões.

Crie o menor contrato necessário para os planners reais existentes.

### Utility

Não implemente uma única equação universal para todas as decisões do bot.

Use política híbrida:

1. hard constraints;
2. classes de prioridade quando necessário;
3. score contínuo apenas entre alternativas comparáveis;
4. custo de assignment no Engine.

Exemplos de hard constraints:

* precisa atacar air;
* precisa de detector;
* unidade não pode ser worker;
* unidade precisa chegar dentro do deadline;
* unidade deve estar disponível para preemption.

Uma opção incompatível deve ser rejeitada, e não receber apenas uma penalidade numérica.

Entre opções elegíveis, uma utility pode considerar termos como:

```text
strategic_value
urgency
information_gain
tactical_risk
travel_cost
opportunity_cost
```

Mas cada termo deve ter semântica clara e ser observável nos logs.

Não introduza pesos arbitrários sem necessidade real.

---

## 4. Body

Body representa:

> Como a intenção escolhida vira uso concreto de unidades e comandos no jogo?

Body contém:

```text
Engine
+
Behaviors
+
integração operacional com Ares
```

### Engine

O Engine continua sendo a única autoridade de ownership.

Ele decide **quem** executa uma proposta.

O Engine pode evoluir de `count` para algo como:

```text
minimum_power
desired_power
required_capabilities
preferred_capabilities
suitability
travel_cost
opportunity_cost
previous_owner
commitment
preemption_margin
```

Mas não deve decidir se devemos atacar, defender ou scoutar.

Essa decisão pertence ao Ego.

O Engine resolve problemas como:

```text
"Defense precisa de 14 ground power e prefere siege."

Quais unidades disponíveis atendem melhor isso?
```

No estágio atual, prefira um algoritmo greedy determinístico e explicável.

Não introduza:

* ILP;
* solver global;
* optimizer genérico;
* planner universal de recursos;

sem evidência concreta de que o greedy atual não resolve.

### Ownership e Ares

O Engine deve continuar sendo a fonte única de verdade de ownership.

Se `UnitRole`, squads ou mecanismos equivalentes do Ares forem usados, eles devem espelhar o grant do Engine.

Nunca permita:

```text
Engine diz que unidade pertence a Defense
```

enquanto:

```text
Ares Squad/Role trata a mesma unidade como pertencente a Attack
```

Não crie duas autoridades de posse.

### Behaviors

Behaviors decidem **como** executar a intenção já aprovada.

Exemplos:

* movimentação;
* pathing;
* siege/unsiege;
* stim;
* heal;
* focus fire;
* stutter;
* retreat movement;
* formação;
* execução de scout.

Behaviors não devem começar a escolher prioridades estratégicas globais.

---

# Consideração importante sobre Command e Behavior

Verifique se atualmente o dispatch de behavior está implicitamente associado ao tipo de comando.

Evite uma arquitetura onde algo como:

```text
ATTACK → DefenseBehavior
HOLD → CoreArmyBehavior
SCOUT → ScoutBehavior
```

faça o tipo de comando determinar automaticamente qual vertical deve executar.

Quando Attack, Harass, Defense e MapControl coexistirem, vários behaviors poderão usar comandos semelhantes.

Considere separar claramente:

```text
executor / behavior
```

de:

```text
command / action
```

Exemplo conceitual:

```text
executor = DEFENSE
action = ATTACK
```

ou:

```text
executor = ATTACK_ARMY
action = ATTACK
```

Não precisa criar um framework para isso; apenas evite colapsar identidade da missão e ação física no mesmo enum.

# Prioridade de implementação

Siga o roadmap de `docs/propostas.md`.

Não tente implementar tudo de uma vez.

A ordem conceitual preferida é:

## P0.1 — avaliação reproduzível

Antes de tunar inteligência, criar um baseline reproduzível.

Precisamos conseguir responder:

```text
esta mudança melhorou alguma coisa?
```

Registre de forma reproduzível:

* commit;
* Ares SHA;
* configuração;
* mapa;
* raça/oponente;
* resultado;
* duração;
* replay;
* logs;
* motivo de término.

Não considere uma partida isolada como evidência.

---

## P0.2 — corrigir defesa

Prioridade alta.

Implemente a defesa em torno de incidentes e déficit de resposta.

Fluxo desejado:

```text
Attention
    ↓
enemy observations

Awareness
    ↓
ThreatIncident
incident_power
affected_assets
confidence
capabilities

Ego / Defense Planner
    ↓
required_power
existing_suitable_cover
reinforcement_deficit

Proposal
    ↓

Body / Engine
    ↓
unit assignment

Body / Defense Behavior
    ↓
intercept / defend / engage
```

Use o caso do SCV que gerou múltiplas respostas como teste de regressão.

Um único nuisance/scout não deve retirar Marine + Marauder + Tank de lugares diferentes simplesmente porque o kernel toca múltiplas bases.

---

## P0.3 — criar ciclo ofensivo

O bot precisa conseguir vencer uma partida.

Implemente uma fatia ofensiva simples e persistente antes de criar sistemas genéricos.

Estados possíveis:

```text
ASSEMBLE
ADVANCE
ENGAGE
RETREAT
REGROUP
SEARCH
```

Isso pode pertencer ao planner/behavior adequado sem introduzir uma camada nova.

Responsabilidades:

### Awareness

Fornece:

```text
known enemy targets
enemy estimates
region state
information confidence
local force estimates
```

### Ego / Attack Planner

Decide:

```text
quando atacar
qual objetivo atacar
quando cancelar
quando reagrupar
quando procurar novo alvo
```

### Body / Engine

Decide:

```text
quais unidades compõem a força
```

### Body / Behavior

Executa:

```text
movimento
engage
retreat
siege
micro
```

Use combat simulation do Ares como uma evidência local para engage/retreat, não como Strategy global.

---

## P0.4 — macro resiliente mínima

Antes de diversificar builds, permita que a macro:

* sobreviva a rush;
* interrompa/adapte opening em emergência;
* reponha infraestrutura;
* controle supply;
* continue upgrades;
* lide com detecção básica;
* mantenha produção;
* reduza recursos parados.

A política continua no projeto.

Use Ares para mecanismos já existentes de produção/tech/upgrades quando apropriado.

Não reimplemente executor de macro apenas para manter tudo “nosso”.

---

## P1.1 — informação recorrente

Depois do scout inicial, Awareness não pode transformar desconhecimento em `enemy_power = 0`.

Separe explicitamente:

```text
known_enemy_power
estimated_enemy_power
uncertainty
coverage
confidence
```

Não é necessário Bayes completo.

Um modelo conservador simples e observável é preferível.

Intel Planner deve conseguir formular perguntas como:

```text
Existe terceira base?
Existe air tech?
Existe cloak?
Onde está o exército?
Qual rota de ataque é provável?
```

Scouting deve responder perguntas, não apenas visitar waypoints.

---

## P1.2 — RegionState

A topologia existente precisa começar a produzir decisões.

Crie uma representação de Awareness parecida com:

```text
RegionState
    region_id

    own_power
    known_enemy_power
    possible_threat

    control
    information_age

    base_value

    neighbours
    ingress_risk
    egress_risk
```

Não precisa conter todos esses campos imediatamente.

Adicione somente os que tiverem consumidores reais.

Primeiros consumidores esperados:

```text
Defense
Attack
Intel
Economy
```

Exemplos:

```text
Defense:
escolher intercept/choke

Attack:
escolher target/corredor

Intel:
escolher região cuja informação está velha

Economy:
penalizar expansão sem rota/cobertura
```

Não refine kernels, lattice ou resolução antes de o modelo atual gerar decisões mensuráveis.

---

## P1.3 — combate Terran incremental

Não tente implementar micro de todas as unidades.

Evolua verticalmente:

```text
1. squad coeso
2. engage/retreat
3. target scoring
4. Marine/Marauder
5. Tank
6. Medivac
7. avoidance/splash
```

Use primitives do Ares sempre que já resolverem o mecanismo operacional.

Nossa inteligência deve decidir política; Ares pode executar mecanismos genéricos.

# Regras matemáticas

Queremos substituir árvores de `if` por modelos contínuos somente quando existir uma grandeza contínua real.

Boas candidatas:

```text
threat
combat power
confidence
uncertainty
control
information age
travel cost
regional value
reinforcement deficit
target utility
assignment suitability
```

Má candidata:

transformar toda decisão estratégica do bot numa única soma ponderada.

Matemática deve reduzir complexidade conceitual, não escondê-la.

Prefira:

```text
reinforcement_deficit =
    max(0, required_power - suitable_cover)
```

a:

```text
if enemy_count > X:
    if tanks > Y:
        if base_is_natural:
            ...
```

Mas preserve `if`s quando representam fatos discretos reais:

```text
unit can attack air?
detector required?
upgrade researched?
mission expired?
structure exists?
```

Essas condições não precisam virar scores.

---

# Observabilidade é requisito

Qualquer nova decisão importante deve aparecer na trilha causal existente.

Precisamos continuar conseguindo responder:

```text
Por que esta unidade fez isso?
```

Para cada nova decisão relevante, registre os inputs suficientes.

Exemplo Defense:

```text
incident_id
incident_power
confidence
affected_assets
required_power
existing_cover
reinforcement_deficit
requested_capabilities
granted_units
rejected_units
release_reason
```

Exemplo Attack:

```text
candidate_targets
selected_target
local_force_ratio
information_confidence
engage_reason
retreat_reason
target_switch_reason
```

Não adicione matemática que não possa ser diagnosticada posteriormente.

---

# Não fazer

Não:

* recriar a arquitetura da branch `matematização`;
* criar novas camadas entre Attention, Awareness, Ego e Body;
* criar Manager/Service/DTO para cada substantivo;
* criar StrategyInputs apenas para copiar Awareness;
* criar MissionBoard genérico antes de necessidade concreta;
* criar MissionPolicy universal;
* criar SquadController paralelo ao Engine/Ares;
* introduzir event bus;
* criar dependency injection framework;
* criar solver global;
* introduzir RL;
* introduzir rede neural;
* criar belief probabilístico complexo agora;
* reimplementar pathfinding, micro ou grids genéricos que o Ares já resolve;
* misturar ownership do Engine com ownership independente do Ares;
* transformar ausência de informação em certeza;
* refinar a matemática espacial sem consumidores reais;
* copiar subsistemas inteiros da `matematização`.

Se lógica antiga for reutilizada, extraia apenas:

```text
algoritmo
heurística
FSM
matemática
comportamento comprovadamente útil
```

e adapte à arquitetura atual.

# Regra de crescimento

Antes de criar uma nova abstração, responda:

1. Qual problema concreto ela resolve?
2. Qual das quatro camadas é dona desse problema?
3. Já existe um módulo nessa camada que poderia resolver isso?
4. Existem pelo menos dois consumidores reais?
5. Isso reduz o caminho causal ou aumenta?
6. Conseguiremos explicar a decisão no log?
7. Existe teste ou cenário que justifique a mudança?

Se essas respostas não forem fortes, não crie a abstração.

---

# Forma de trabalho

Antes de modificar código:

1. leia `docs/propostas.md`;
2. inspecione o código atual;
3. identifique quais recomendações já estão implementadas;
4. identifique a menor mudança coerente com o roadmap;
5. preserve as quatro camadas;
6. liste os arquivos que pretende alterar;
7. explique em qual camada cada novo conceito pertence.

Depois implemente incrementalmente.

Ao final de cada etapa, reporte:

```text
Problema resolvido
Arquivos alterados
Camada responsável
Nova responsabilidade adicionada
Responsabilidades que NÃO foram adicionadas
Testes adicionados/alterados
Logs adicionados
Riscos ou dívida restante
```

Se durante a implementação surgir a necessidade aparente de uma quinta camada arquitetural, pare.

Primeiro tente representar o problema como especialização interna de:

```text
Attention
Awareness
Ego
Body
```

A arquitetura atual é um ativo do projeto. A meta agora é fazer a inteligência e o gameplay crescerem sobre ela, não substituí-la.
